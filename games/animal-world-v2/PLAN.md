## 1. 배경

### 1.1 지금 구조(v1)

모든 그림을 코드로 그리고 이미지 파일은 쓰지 않는다. 렌더러는 Canvas 2D 하나다.

| 영역 | 방식 | 위치 |
|---|---|---|
| 하늘 | 매 프레임 그린다(시간대 팔레트 `lightAt`) | `art.js` `drawSky` |
| 땅·바닥 물건 | 40×66칸 쿼터뷰 지형을 한 장으로 미리 그려 캐시한다. 확대 배율이 바뀌면 다시 그린다 | `index.html` `islandArt`, `art.js` `drawIsland` |
| 서 있는 물건 | 물건마다 스프라이트로 한 번 그려 캐시한다 | `itemSprite`, `items/*.js` |
| 동물 32종 | 관절 리그(rig, 뼈대·IK·스프링)로 **매 프레임** 벡터 경로를 그린다 | `rigs/<종>.js`(약 9천 줄) |
| 외곽선 | 보이는 동물을 큰 캔버스 `atA`(2048×최대 4096)에 모아 그리고, 8방향 밀어 찍기 + `source-in`으로 테두리를 만든 `atB`를 장면에 찍는다 | `index.html` `packOutlined` |
| 가림 | 언덕·봉우리 칸을 동물과 깊이 순서로 다시 찍는다 | `stampColumn` |
| 파티클 | 물보라·흙먼지를 `arc()`로 그린다 | `index.html` `parts` |
| 시간대 빛 | 장면 전체에 `source-atop`으로 색을 덧입힌다 | `index.html` `draw()` 끝 |

### 1.2 왜 바꾸나

- 지금 구조는 효과를 늘릴 여유가 적다. 외곽선 하나 때문에 44마리에서 38fps까지 떨어진 적이 있다(DESIGN.md 14절, 아틀라스로 해결).
- 물빛·하이라이트·빛 번짐 같은 효과는 픽셀 단위 계산이라 Canvas 2D로는 비싸다. GPU의 셰이더(shader, 픽셀마다 동시에 실행되는 작은 프로그램)로는 싸다.
- 노트북 가로 화면은 그릴 픽셀이 휴대폰 세로 화면보다 훨씬 많다(예: 1440×900 화면 배율 2 = 약 520만 픽셀).

### 1.3 짚어 둘 점

- 참고 사례(geoje-jelly)의 **젤리 출렁임은 WebGL 기능이 아니다**. CPU의 감쇠 스프링 값을 변형 행렬에 넣은 것이다. Animal World 리그도 이미 스프링(`springTo`)을 쓰므로 v1에서도 낼 수 있다. 렌더러 전환의 근거는 "젤리 효과"가 아니라 1.2의 성능·효과 여유다.
- PixiJS는 **그림 그리는 작업을 대신하지 않는다**. 리그 32종은 그대로 Canvas 2D로 그리고, PixiJS는 그 결과를 받아 합성한다.

### 4.2 바뀌는 것과 그대로인 것

| 파일 | v2에서 |
|---|---|
| `logic.js`, `data.js`, `terrain.js`, `music.js`, `sound.js`, `sounds/` | 그대로 |
| `art.js`, `rigs/*.js`, `items/*.js` | 그대로(그림 결과를 텍스처로 넘기기만 함) |
| `index.html` `draw()`와 그리기 함수들 | 새 모듈로 분리: `render/render2d.js`(v1 그대로 옮김), `render/renderPixi.js`(새로 작성) |
| `index.html` CSS·HUD·시트 | 가로 레이아웃 추가(M4) |
| `sw.js` | PixiJS 파일과 `render/*.js`를 캐시 목록에 추가, `CACHE` 버전 올림 |
| 새 파일 | `vendor/pixi.min.mjs`(버전 고정), `render/*.js`, `tools/perf.html`(측정) |

렌더러는 같은 인터페이스를 갖는다: `init(canvas)`, `resize(VW, VH, DPR)`, `draw(dt)`, `invalidate(kind)`(땅·물건 캐시 다시 만들기), `destroy()`. 입력 판정(`tileAtScreen` 등)은 화면 좌표 계산이라 렌더러와 무관하게 유지한다.

### 4.3 동물 그리기 경로(핵심)

```
매 프레임
 ① 보이는 리그 동물을 atA(Canvas 2D)에 그림        ← 지금 코드 그대로
 ② atA 텍스처 갱신: texture.source.update()        ← CPU→GPU 업로드(가장 큰 위험)
 ③ 외곽선 필터로 atA → atB(RenderTexture) 한 번에    ← GPU 패스 1회(지금은 8회 밀어 찍기)
 ④ 동물 Sprite마다 atB의 자기 칸(frame)을 가리킴      ← 배치되어 드로우콜이 적음
```

- 외곽선은 Sprite마다 필터를 걸지 않는다. 필터가 많으면 오히려 느려지므로 아틀라스 전체에 한 번만 건다.
- ②의 업로드 비용은 아틀라스에서 실제로 쓴 높이에 비례한다. M1 시제품에서 먼저 잰다. 대응책은 7절.
- 아틀라스가 다 차면(크게 확대) 넘친 동물은 작은 캔버스에 따로 그려 별도 텍스처로 쓴다(v1과 같은 규칙).

### 4.4 나머지 요소

| 요소 | v1 | v2 |
|---|---|---|
| 깊이 정렬 | `stand.sort()` 후 순서대로 그림 | `depth` Container의 `zIndex`. 값이 바뀐 것만 다시 정렬 |
| 가림 칸 | 겹친 동물이 있을 때 칸 그림을 다시 찍음 | 칸마다 Sprite를 미리 두고, 겹칠 때만 `visible = true` |
| 확대(핀치·휠) | 그려 둔 그림을 늘리고, 멈추면 다시 그림 | `world.scale`로 늘리고, 멈추면 땅·물건 텍스처를 그 배율로 다시 만듦(같은 정책) |
| 시간대 빛 | `source-atop` 색 덮기 | `world`에 색 필터 하나. 하늘은 필터 밖 |
| 파티클 | `arc()` | `ParticleContainer` + 원 텍스처 하나 |
| 선택·놓을 자리 표시 | 경로 그리기 | `Graphics`(바뀔 때만 다시 만듦) |
| 땅 크기 제한 | 최대 1,200만 픽셀(iOS 한도) | 노트북은 GPU 텍스처 최대 크기(`MAX_TEXTURE_SIZE`, 보통 8192~16384)에 맞춘다. 넘으면 타일로 나눈다 |

### 4.5 예외 처리

- **WebGL을 못 쓰는 브라우저**: `render2d.js`(v1 경로)로 돌아간다. 주소에 `?renderer=2d`를 붙여도 v1 경로로 그린다. 비교 측정에도 쓴다.
- **컨텍스트 손실**: 손실 이벤트에서 그리기를 멈추고, 복구되면 캔버스로 만든 텍스처를 모두 다시 올린다. 땅·물건 캐시는 원본 캔버스가 CPU 쪽에 남아 있어 다시 올리기만 하면 된다. `WEBGL_lose_context` 확장으로 강제 시험한다.
- **메모리 정리**: 지역 이동·동물 방생·물건 치우기 때 쓰지 않는 Sprite·Texture를 `destroy()`한다.

### 4.6 PixiJS 넣는 방법

- 빌드 도구가 없으므로 PixiJS ES 모듈 배포 파일을 `vendor/`에 넣고 상대 경로로 `import`한다. CDN은 쓰지 않는다(오프라인 PWA, 버전 고정).
- 버전은 8.x 중 하나로 고정하고 파일 이름에 버전을 넣는다. 인터넷 예제 상당수가 v7 문법이라 공식 v8 문서만 참고한다.
- 추가 필터가 필요하면 `pixi-filters`에서 필요한 것만 가져오거나 짧은 셰이더를 직접 쓴다.

## 5A. 바닷속·땅속 단면(바닷가부터)

참고 사례는 섬 덩어리의 잘린 면에 지층을 보여 주고, 물을 반투명하게 그려 물밑 지형과 물고기가 보이게 했다. v2에서는 이를 2D 쿼터뷰로 옮긴다.

### 5A.1 지금 상태와 걸림돌

- 땅 아래 단면은 이미 있다. 다만 얇은 흙 띠 하나다(`art.js` `slabOf` = 땅 크기 × 0.075).
- 바다 칸(`~`)은 높이 −1의 평평한 물 윗면만 그린다. 물밑은 없다.
- **바닷가 지도는 바다가 뒤쪽(0~12행)에 있다**(`terrain.js` `MAPS.seaside`). 쿼터뷰에서 보이는 잘린 면은 앞쪽 두 면이라, 지금 그대로면 **바다 단면이 거의 보이지 않는다**(오른쪽 면 뒤 끝 몇 칸뿐).
- 지도를 뒤집으면 세이브 안 물건·동물 좌표가 어긋나므로 지도는 바꾸지 않는다.

### 5A.2 보여 주는 방법

| 방법 | 내용 | 바닷가 지도에서 |
|---|---|---|
| ① 물 윗면을 반투명하게 | 바다 칸 아래에 물밑(모래 바닥·바위·해초·산호)을 그리고, 물 윗면을 깊이에 따라 반투명하게 덮는다. 물고기는 그 사이에서 헤엄친다. 커스틱(물밑 빛무늬)·잔물결은 셰이더로 | ✅ 바다가 어디 있든 된다. **기본안** |
| ② 잘린 면 단면 | 앞쪽 두 잘린 면을 깊게 만들고, 땅 칸 아래는 지층(겉흙·모래·자갈·암반 띠), 바다 칸 아래는 유리처럼 비치는 물 벽과 그 안의 물밑을 그린다 | 땅속 지층은 잘 보인다. 바다는 오른쪽 면 일부만 |
| ③ 시점 180° 돌리기 | 화면 투영만 반대로 해서 바다를 앞쪽에 둔다(규칙·세이브는 그대로) | 바다 단면이 크게 보인다. 대신 물건 그림·깊이 정렬·탭 판정을 모두 반대 방향으로 다시 맞춰야 해서 작업이 크다. **나중 선택지** |

①+②로 시작한다. ③은 ①②를 본 뒤 필요하면 검토한다.

### 5A.3 구성 요소

| 요소 | 방식 | 규칙 영향 |
|---|---|---|
| 깊어진 섬 덩어리 | 단면 두께를 키우고 지층 띠를 그린다(땅 캐시에 함께) | 없음 |
| 물밑 지형 | 바다 칸마다 바닥 깊이(해안에서 멀수록 깊게)를 정하고, 모래 물결·바위·해초·작은 산호를 시드 난수로 흩뿌린다 | 없음(그림만) |
| 물 표현 | 물밑을 먼저 그리고, 물 윗면을 깊이에 따라 진해지는 반투명 층으로 덮는다. 커스틱·잔물결은 필터 | 없음 |
| 물고기 | 장식용 무리(몇 종, 수십 마리). 간단한 군집 규칙(Boids)으로 바다 칸 안에서만 헤엄친다. 리그 대신 단순한 그림을 아틀라스로 | 없음(그림만) |
| 헤엄치는 동물 | 해달·돌고래는 지금처럼 수면선에 걸쳐 그리되, 물밑 부분은 물 층 아래에 그려 반쯤 잠겨 보이게 한다 | 없음 |
| 기존 산호초(`reef`) 물건 | 물밑과 어울리게 다시 그린다 | 없음 |

### 5A.4 정해야 할 것: 물고기·산호를 게임 요소로 할까

- **장식(기본안)**: 물고기와 물밑 산호는 그림일 뿐 발전도·인기점수와 무관하다. 규칙을 바꾸지 않아 v1 세이브와 그대로 호환된다.
- **게임 요소**: 물고기를 입양하거나 산호를 바닷속에 놓아 발전도가 오르게 한다. `data.js`(새 동물·물건), `logic.js`(바다 칸에 놓기, 물속 이동), 밸런스 봇, 테스트를 고쳐야 하고 세이브 형식이 바뀐다. v2 범위가 크게 늘어난다.

먼저 장식으로 만들어 보고, 재미가 확인되면 게임 요소로 넓히는 순서를 권한다.

### 5A.5 남극으로 넓힐 때

같은 구조에 물 색(차갑고 맑게), 물밑(자갈·얼음 밑면), 물고기 종류만 바꾼다. 빙산 물건은 물속 아랫부분을 그려 넣는다.

## 8. 측정 방법

- 대니님 노트북에서 `tools/perf.html?region=<지역>&n=44&zoom=<배율>&renderer=<2d|pixi>`를 열고 30초 평균 fps, 1% 최저 fps, 단계별 시간을 표로 기록한다.
- 원격 세션의 헤드리스 Chrome은 소프트웨어 WebGL이라 **GPU 수치로 쓸 수 없다**(하위 세션도 같은 문제를 겪었다). 원격에서는 그림 일치·오류 확인만 하고, 성능은 노트북에서만 잰다.

## 9. 모바일 타진(v2 완성 뒤)

- 대상: 휴대폰 가로 화면. 화면 배율 상한(지금 2), 텍스처 크기(iOS 메모리), 발열·배터리를 본다.
- 판단: 3절과 같은 장면에서 30fps 이상이면 가로 모바일 지원을 진행, 아니면 v1 경로를 모바일 기본으로 남긴다.
- 정할 것: 모바일을 가로 기본으로 바꿀 때 세로 화면을 계속 지원할지.
